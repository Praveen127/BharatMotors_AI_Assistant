Generated by `python scripts/run_agent.py --demo`, which drives
`agent.core_agent.SupportAgent` (mode=`full`) through five scripted turns
across two sessions, logging every interaction to `logs/interactions.log`


**Trace:** `guardrail=refuse` · `latency=0.0ms`

## Turn 5 — Compound request containing "recall" → escalated as a whole
**Session:** `demo_session_2` · **Interaction ID:** `16dedc73fc21`

> **User:** Never mind — can you find the nearest service center for PIN
> 560001, and also tell me if my Bharat Volt has a pending recall?
>
> **Agent:** I want to make sure this is handled properly, so I'm escalating
> it to a specialist who can look into it in detail. Your ticket ID is
> BM-174708 (SLA: within 4 business hours).

**Trace:** `guardrail=escalate_high` · ticket `{severity: HIGH, category:
"recall/legal/repeated-complaint case"}` · logged issue summary shows
`PIN [PIN_CODE_REDACTED]` — **the raw PIN code was never written to the
log.**

**What this demonstrates:** Two things at once. (1) PII-safe logging:
`safety/pii_filter.redact()` is applied to the issue summary before it's
persisted in the escalation ticket log. (2) A deliberate design decision —
guardrails run on the **whole** message before `agent/planner.py` gets a
chance to decompose it into sub-tasks. Because this message mentions
"recall," it is escalated as a single HIGH-severity case rather than
partially answered by the service-center-locator tool and partially
escalated. `docs/evaluation_report.md` (test case TC10) demonstrates the
planner successfully splitting a compound question that does *not* trip a
safety/escalation trigger, so both behaviours are independently verified.
